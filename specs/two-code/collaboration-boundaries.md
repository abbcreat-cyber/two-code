需要验证的场景：待审批时连续补充、重复requestId；命令真实失败后的同会话续接；Host重新加载已保存任务后不自动执行，显式续接仍复用角色会话。真实任务覆盖正常链路；存储失败、底座更新拒绝以确定性故障夹具覆盖，不将注入故障称为上游真实事故。

故障夹具已复现两个边界：运行中补充保存失败后旧计划仍继续；副手更新未确认时能以旧报告完成。规则：未确认的新要求不能变成成功，也不能继续旧计划。Coordinator是唯一所有者，使用现有AbortSignal停止两角色；保存失败必须显式报告，不静默吞掉。app层共用更新失败处理：记录已有steeringError、追加错误事件，立即abort，再尝试保存错误状态；二次保存失败也在错误中报告，不因保存阻塞延迟停止。用户requestId失败标记继续沿用deliveryFailed。

```text
用户补充/主手更新 → Coordinator记录新要求 → 保存/原生update
                                                 ├─ 确认：继续同一会话
                                                 └─ 失败：错误事件 → abort → 收尾持久化
重复requestId → 复用原准入结果（失败仍为失败）
Host重开 → 读取同一日志与会话ID → 用户显式请求才启动
```

事件及错误状态沿用现有任务日志，桌面连续流和重开快照使用同一投影，不增加第二份状态或自动重试。已经发生的副作用不假定回滚。

# Two Code视觉通路

用户任务36288112-b508-4700-9e05-375d64edd578实测：Pi/腾讯DeepSeek配置原有image输入，并非模型不支持视觉。任务产出SVG后没有渲染工具，工具桥仅能返回文字，Two Code输入框也未接图片采集。修复应用的像素传递能力，不改用户模型/底座或认证。

## 唯一所有者和链路

Host图片适配器拥有图片文件的读取、格式检查、SVG渲染和缓存。Coordinator仍拥有执行/权限状态。上传只存图片附件，不启动模型。UI复用原输入框附件入口和样式，提供选择、拖入和粘贴；上传成功产生持久绝对路径，草稿保留引用，发送仍用原submit路径。两角色按同一引用用view_image读取，不能以文字转述替代图片。不向前端暴露密钥，不把base64写进任务事件。

历史投影从应用生成的完整图片引用中还原原版附件卡，不改写模型上下文和事件原文。readImage仅读取当前Host导入目录下的内容哈希命名图片；用原生readAttachment回调供消息缩略图和大图预览使用，任意其他路径拒绝。发送成功仅清除当次冻结附件ID，不能误删发送期间新增的同一图片。

```text
图片选择/粘贴 → Host附件文件 → 原submit中的图片引用
SVG/PNG/JPEG等路径 → view_image → Host读取/渲染 → 原生工具image内容块 → 模型
                        └→ visual事件（来源/预览路径）→ 原版工具行及回放
```

view_image同时提供给Pi/Step/Claude/ZCode；Pi/Step扩展直接返回原生image内容，MCP返回image内容，禁止把对象字符串化成文字。SVG使用内置渲染器生成PNG像素，无需搜索系统命令或操作浏览器。SVG不加载外部资源、不执行脚本；图片数量、文件大小、渲染尺寸均有界，失败明确报告，不默认为视觉不支持。文件只读遵循现有任务权限；只在Host私有目录缓存渲染产物。

不因为渲染器缺失而否定模型视觉能力；只有真实图像请求遭底座/API拒绝时才报告该通道不支持。SVG源码校验不等于视觉验收。上传附件目录保持在D盘，已发送引用跨刷新/重启可读。

真实测试发现第二处丢图：Claude原生记录保留了tool_result中的image块，但本机wb-direct的Messages→Chat转换对tool_result调用anthropicText，只留下文字；顶层image转换正常。Two Code为本轮Claude本机连接创建私有转发器，将工具图片保持为同一user消息的顶层原生image块，保留tool_use_id和全部文字/顺序；不修改模型、不走额外视觉模型、不改共享网关或重启3090。会话结束关闭此转发器，鉴权头仍交给原配置的上游，不保存请求内容。

第一轮兼容修复仍未生效，继续查出未编辑的Claude原生连接在freeze中返回undefined，绕过适配层连接装配。现在有明确API地址的Claude本机连接也以准入时快照交给适配器；未配置API地址的原生订阅认证不变。每轮仅保存请求数、图片块数及base64字符数用于证据核对，不保存请求体或凭据。
